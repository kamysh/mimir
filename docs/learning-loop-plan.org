  OpenRouter, DeepSeek, Z.ai, Gemini, and an explicit compatible endpoint.

- Preserve uncommitted work until its explicit replacement/removal step. Do not
  rewrite existing commits or discard unrelated files as routine cleanup.
- This plan does not authorize live settings changes, account setup, email
  delivery, production belief mutations, scheduling, publishing, or deployment.

* Recommendation

Use GPT-6.1 Sol for most Rust implementation, GPT-6 Luna for tightly specified
mechanical work, and GPT-6 Astra for the formal model and focused reviews of
revision, inference, and concurrency correctness. Do not use a frontier model
for every fixture, documentation edit, or command execution.

These assignments are engineering recommendations, not measured comparative
benchmarks on this repository. Start with small, observable tasks and retain
only models whose results meet the same acceptance criteria.

Use one implementer at a time in the existing worktree. Model assignments do
not imply permission to spawn agents or concurrently modify the checkout.
A separate review can be a later sequential session with only the relevant
contract, diff, and receipts.

** Correctness decisions before porting

1. Specify whether grounding changes numerical evidence during propagation,
   and distinguish that from adding GROUNDS to the belief-edge substrate.
   Reconcile the existing Evidence theorem, the original integration test, and
   the new implementation. Do not weaken the theorem to make the code pass.
2. Specify what is reversible: review-owned evidence/edges are reversible;
   separately created beliefs and patterns currently are not. Preserve this
   distinction unless a separately agreed design extends ownership.
3. Specify the treatment of the same incident recorded both as a belief and as
   an experience. Prompt instructions alone are not a general deduplication
   guarantee. The minimum target is one evidence contribution for an identified
   incident; arbitrary semantic deduplication is not promised.
4. Keep schema/revision, credential, and tool-scope checks mandatory. They are
   application correctness checks, not agent interaction gates or memory quotas.
5. Decide whether to retain one =max_calls= bound or separate model/tool limits.
   Recommendation for the first port: retain existing semantics and document
   them; do not silently add a larger allowance.

** Cost-control rules for development

- Prefer Sol medium for a normal Rust step; use high when concurrency, process
  lifecycle, credential handling, or multi-module reasoning warrants it.
- Use Luna low/medium only after the interface and expected behavior are fixed.
  Do not ask it to independently choose inference semantics or revise proofs.
- Give Astra the contracts, disputed functions, and failing counterexample,
  not the entire historical conversation. Use high rather than max by default.
- Stop after two failed repair attempts on the same cause. Escalate the smallest
  failing case to the recommended stronger model instead of replaying the task.
- Require an exact diff, checks, and remaining issues at handoff. Preserve a
  concise receipt so the next model does not rediscover the repository.
- Run deterministic fixtures before paid live calls. Do not repeatedly call
  real LLMs to debug TOML parsing, SMTP sockets, or a malformed test fixture.
- Use standard processing. Fast/ultrafast is not a cost optimization. Batch
  discounts are not assumed for an interactive, dependent tool loop.
- Record input, cached input, output, and actual provider/harness cost when
  available; report unknown usage as unknown rather than inventing a charge.

A transparent planning scenario: 2M input/0.3M output on Luna costs USD 0.35;
4M/0.6M on Sol costs USD 14; 0.6M/0.1M on Astra costs USD 11. Total: USD 25.35.
The same 6.6M/1M tokens entirely on Astra would cost USD 116. This illustrates
allocation savings under equal token volume; real models can need different
numbers of attempts and tokens. It is not a quote, cap, or spending approval.

**** Command surface and compatibility

Use one =Judge= subcommand group in the existing =mimir= binary:

#+begin_example
mimir judge check-config [--config PATH]
mimir judge run [--config PATH] [--state-dir PATH]
mimir judge status [--state-dir PATH]
#+end_example

=check-config= parses and validates the selected TOML locally. It does not start
MCP, open the database, contact an LLM or SMTP server, or create a state file.
=run= processes one bounded pending batch and writes local status. =status= reads
only the last local report and can return a =never_run= result when it is absent;
it does not infer database completion from a file. Existing =mimir= commands and
=MimirService= keep their present behavior when =[judge]=, =[llm]=, and =[email]=
are absent. A judge invocation requires valid judge and LLM settings; email
remains optional. No independent =mimir-judge= executable or Python fallback is
part of this interface.

**** Configuration and private files

Resolve one config path for a judge invocation in this order: explicit =--config=,
then =MIMIR_CONFIG=, then =XDG_CONFIG_HOME/mimir/config.toml= (falling back to
=~/.config/mimir/config.toml=). Resolve a relative explicit path against the
launch directory before starting a child, and pass the resulting absolute path
through =MIMIR_CONFIG= to =mimir-mcp=. Do not change process-global environment
to select a file; the Rust loader should accept an explicit path. Preserve the
existing =[database]= and optional =[embeddings]= sections, and parse the
existing =[judge]=, =[llm]=, and =[email]= names from
=runtime/config.example.toml= without gratuitous renaming. No provider/model
fallback is allowed. Unknown runtime fields, invalid combinations, limits,
credential settings, and endpoints must fail validation with redacted messages.

The existing core writes new config files with a private directory and file;
the judge should validate ownership/access on the selected file and must not
chmod, replace, or print the user's existing config. A private directory
(mode 0700) or a private regular file (mode 0600) is accepted only where the
other path components cannot expose the file; the exact permission check and
symlink policy belong to Step 4's typed validator. This is intentionally open
until its safe implementation is reviewed.

Resolve state from explicit =--state-dir=, then an absolute =XDG_STATE_HOME/mimir=,
then =~/.local/state/mimir=. State belongs to the user, is created by =run= with
mode 0700, and holds only private atomic status/outbox/token files (mode 0600)
and a per-state-directory lock. =status= is read-only and distinguishes missing
state from a successful idle run. A stale file is a historical report, not a
live process or proof of pending work. Step 5 specifies lock and crash behavior.

**** Transport and visible outcomes

The initial judge starts the configured =mimir-mcp= child over stdio JSON-RPC.
The child receives the exact selected config path. Host code verifies the
learning tool schemas and permits only the explicit review tool allowlist,
pinned batch revisions, and selected project scope; a model cannot call arbitrary
MCP tools. The database's committed revision, not model prose or a status file,
establishes review completion. Direct in-process service calls are deferred.

Each command emits one machine-readable JSON result on stdout. Diagnostics go to
stderr, without configuration source lines, credentials, belief bodies, raw LLM
or SMTP response bodies. =check-config= reports =valid= or =invalid_config=.
=run= reports =idle= (no pending work, no model call), =complete= (every selected
revision confirmed), =partial= (some revisions remain/deferred), =blocked=
(no trustworthy progress), or =already_running= (lock not acquired). It records
an independent notification outcome: =disabled=, =not_needed=, =sent=,
=retry_pending=, or =exhausted=. A notification failure must not change a
confirmed review from =complete= to =partial=. =status= returns the last report
or =never_run= and its recorded time, explicitly marked as a snapshot.

Exit status must distinguish successful idle/complete from invalid config,
partial/blocked work, and lock contention; the exact numeric map and JSON field
schema are deferred to Step 4's CLI implementation, where they can be verified
against callers. No class of transport/model failure may be printed as a
successful =complete=. Step 5 defines the transition rules and retry semantics.

*** Astra actions 2–8 — Learning and runner contracts

**** Revision, ownership, and acknowledgement

An incident is identified by its caller-stable experience UUID. Its project is
immutable. A correction keeps that UUID and increments the source revision;
it is not another independent observation. Source and review revisions are
separate monotonically increasing counters. Current immutable source/review
versions are selected by pointers, not by summing historical rows.

The existing source-write contract is retained: an identical payload with
expected revision equal to the current revision or its predecessor is a retry;
otherwise the expected source revision must equal the current revision before
a correction is accepted. A changed project is always refused. Bounded Rust
counters must reject overflow; Agda uses unbounded natural numbers.

A review request names the experience UUID, the exact source revision, and the
expected review revision. A stale source is refused even if its payload matches
an old review. An exact replay of the active review with expected review revision
=current= or =current - 1= returns the existing result. All other requests must
match the current review revision. Retry equality includes reviewer identity,
rationale, candidate declarations, resolved targets, and the complete effect
bundle; use a stable canonical request representation, without generated UUIDs
or timestamps making an identical retry different.

Before a new review commits, validate every target and candidate reference,
project membership, evidence prerequisites, finite weights, payload bounds,
and duplicate/conflicting keys. Existing targets must belong to the exact
experience project and must not be Working beliefs. Global retrieval visibility
does not authorize writes to global targets. Host-side checks complement these
server-side checks; the model cannot choose the host's project scope or reviewer.

One transaction must persist the review version, resolve/create its candidates,
replace its owned links and numerical contributions, recompute affected beliefs,
and acknowledge the current source revision. Any failure rolls all those effects
back. A connection loss after sending the request is an unknown commit outcome:
read the database and retry the exact request if necessary. Do not infer rollback
from a missing reply and generate a new identity.

A corrected source immediately deactivates the old review bundle and becomes
pending. A replacement review removes the entire previous owned bundle before
applying the replacement. An empty-effect review acknowledges without adding
support; this is also how a mistaken interpretation is retracted. Immutable
history remains. Manual edges, other experiences' contributions, base priors,
and document grounding are independent and must survive review replacement.
The original =Learning.Contributions= laws remain unchanged; the new contracts
also model guarded transitions, pointwise ownership, and independent manual data.

**** Numerical grounding and project boundaries

There is no contradiction between the two existing formal contracts:

- =Evidence.propagate-evidence-invariant= quantifies over functions of the
  belief-edge list. GROUNDS never becomes a SUPPORTS/DEFEATS/CAUSES edge.
- =Beta.CCoupling= adds positive document evidence mass to the Beta prior used
  for recomputation. That can change a belief's posterior and downstream means.
  It does not claim numerical non-interference.

Recompute from the fixed insertion prior plus current independent evidence:

#+begin_example
alpha = alpha0 + current positive review mass + current grounding mass
        + complete positive incoming-edge mass
beta  = beta0 + current negative review mass
        + complete negative incoming-edge mass
#+end_example

Never start from the previous posterior and add the same evidence again.
=Evidence.Numerical= proves that grounding remains an additive alpha component
for every fixed list of incoming edge quanta and that it does not add beta mass.
Changing source means can change edge quanta; the law does not assert global
linearity of a cyclic graph. Existing convergence and complete-incoming-edge
requirements still apply. Evidence removal must recompute from remaining
sources; merely deleting a GROUNDS edge leaves stale numerical support.

For a review in project P, derive the affected closure inside P. Include targets
of removed effects as seeds as well as new targets. Do not traverse into another
project and back. Persist numerical updates only for P. Preserve every incoming
belief edge to an affected node, including parents outside P; their committed
means are read-only boundary inputs. This prevents missing incoming support
without writing foreign nodes. This is a review-triggered propagation contract;
it does not change the separately invoked general graph-propagation API.

The current =recompute_learning= validates direct targets but then expands over
all projects. Step 3 must fix that gap. It must also replace all-belief/all-edge/
all-review loading with targeted validation, project-restricted affected closure,
complete incoming-edge reads, and relevant active-review/grounding queries.
Paging must not introduce another corpus-size cap. An affected connected
component may itself be large; that cost must be reported, not hidden by a cutoff.

**** Incident deduplication and belief/pattern candidates

Deduplication is exact identity, not semantic similarity. Reusing an experience
UUID prevents retry duplication. Two different UUIDs for the same real-world
incident can still count twice; callers must preserve incident identity. The
judge may flag suspected duplicates for review, but must not silently merge
histories or invent a universal semantic deduplicator.

For new automatic learning, capture the incident once as an experience and use
its atomic candidate/review path. Do not also insert a high-confidence standalone
belief for that same incident and then treat it as independent confirmation. A
legacy standalone belief with no incident ownership cannot be safely stripped
of its prior by this mechanism; identify that overlap for review instead. This
is a remaining capture/provenance limitation, not a deduplication guarantee for
all existing manual beliefs. Step 11 must test the identified-incident path and
report the limits of any prompt-only protection.

The approved Step 3 extension adds candidate declarations to =review_experience=,
with a stable local key and typed payload, and permits typed references to either
an existing UUID or a candidate key in that same review. Existing UUID-only
clients remain valid. The response returns the resolved key-to-UUID mapping.
Server-generated UUIDs, project ownership, and initial numeric state are not
selected by the model.

Persist a registry with a unique =(experience_id, candidate_key)= identity,
the candidate kind, assigned UUID, and immutable original declaration. Reusing
a key with a different declaration is a conflict; a revised claim needs a new
key. Reject a supplied UUID belonging to another experience as a claim of local
ownership. Referencing an existing same-project belief as evidence is allowed
without adopting it. Reserve identities and create graph nodes inside the same
transaction as the review; do not expose standalone =insert_belief= or
=insert_pattern= to this judge. Candidate keys share one namespace per experience;
changing a key from belief to pattern (or conversely) is a declaration conflict.
Validate reference kinds: belief feedback and causal links cannot target patterns.

A new belief candidate starts with a neutral Beta(1,1) prior. Its model-assessed
support/defeat is explicit review-owned feedback, not a permanent high-confidence
insertion prior. Document grounding and later independent reviews remain separate
contributions. Source correction or review retraction removes owned support,
links, and supersession decisions; it does not hard-delete candidate identity,
history, or unrelated work. The same key continues to resolve to the same node.
A retained neutral candidate is a hypothesis, not a verified lesson; no claim of
automatic deletion or invisibility is made by this contract.

Deletion must not free a candidate key for silent recreation. Preserve a retired
mapping/tombstone and refuse an attempt to materialize that deleted identity;
a new intentional candidate needs a new key. Step 3 must coordinate this with
explicit belief/pattern deletion and project deletion, and must not recreate manually
deleted knowledge on an automatic retry. Project deletion remains the explicit
operation that may remove the project's whole registry/history.

The user also approved atomic pattern candidates. A pattern declaration carries
its stable key, kind, situation, and approach. The server assigns the project
and UUID inside the review transaction. Pattern identity and immutable content
follow the same retry, conflict, retention, and deletion rules as beliefs.
Its declaring review owns the provenance association; replacing/retracting the
review or correcting its source removes that association from active evidence,
without deleting the procedure or another experience's evidence for it.

A declaration proposes a procedure; it does not assert that the procedure was
used successfully. New patterns have zero activations and a neutral initial
success-rate value of 0.5, not an LLM-supplied success percentage. Observed
success/failure counts retain the existing current-source =Experience.pattern_id=
contract. Candidate declaration, review retries, retrieval, and model endorsement
do not manufacture observed uses or rewrite the source's pattern assignment.
A later recorded experience may explicitly identify the retained pattern and
contribute its own outcome. Its evidence survives retraction of the original
candidate's declaring review. An untested retained pattern has zero observed
successes/failures and the Beta(1,1) estimate; it is not a verified procedure.

Step 3 must expose candidate provenance through the existing learning inspection
responses, distinguishing an active declaration from retained historical origin.
The generic =Candidates= identity laws and =Revision=/=Learning.Contributions=
active-bundle laws apply to both kinds. Concrete kind validation, atomic graph
creation, and provenance joins are Rust/SQL obligations, not additional claims
made by the abstract proofs.

**** Outcomes and causal hypotheses

Pattern outcomes count the current source version once per experience, not every
review or historical source version. Unknown outcomes add neither a success nor
a failure. AgentReport adds neither regardless of its asserted outcome. Existing
ToolResult/UserFeedback classes are caller-reported provenance, not authenticated
proof. =LearningContracts.Outcomes= formalizes precisely this classification.
An unknown outcome with recorded evidence can still support a justified review
of that evidence; it must not be relabelled as observed task success.

The judge may propose causal hypotheses as typed, weighted, review-owned CAUSES
links between permitted targets. It must distinguish an observed association,
a proposed mechanism, and an actual intervention result in its rationale.
=query_intervention= is read-only propagation through the supplied causal graph;
its output is not independent confirmation of that graph. A successful task or
a high model confidence alone does not establish causal identification. These
claims remain revisable through the same replacement/retraction mechanism.
No autonomous execution of proposed experiments is added in this stage.

**** Runner transitions and refusal

The host fetches one bounded batch and pins each =(experience ID, source
revision, expected review revision, project)=. Failure to fetch is =blocked=,
not an empty successful batch. An empty successfully fetched batch is =idle=
and makes no model call. A nonempty batch enters =running= after the lock and
preflight succeed. =already_running= is a separate refusal before work starts.

At completion, re-read the selected identities from the database. A receipt is
=confirmed= only when the selected source revision is still current and is
acknowledged by a committed current review. A concurrently corrected source is
=corrected=; an unreviewed source is =pending=; a failed/malformed/missing read is
=unavailable=. A newer source is deferred to a later batch rather than silently
changing the work assigned to this invocation.

| Receipts at the final observation | Additional run failure | Learning result |
|----------------------------------+------------------------+-----------------|
| Successful empty fetch           | none                   | idle            |
| Every selected revision confirmed| none                   | complete        |
| Some confirmed, others unresolved| either                 | partial         |
| Every selected revision confirmed| model/transport error  | partial         |
| None confirmed                   | either                 | blocked         |
| Batch fetch failed               | yes                    | blocked         |

A partial result after an error can still report all confirmed reviews; it must
not discard them. Notification errors do not set the learning failure flag.
The report describes a database observation, not a promise that no correction
will occur afterward. Local status files and model completion claims cannot
acknowledge anything. =Judge.Completion= proves that =complete= requires every
receipt to be confirmed and that changing model prose cannot alter the verdict.

The model-visible allowlist is =get_experience=, =experience_history=,
=query_relevant=, =query_learning_context=, =explain_belief=, =get_belief=,
=query_intervention=, =get_contradictions=, and atomic =review_experience=.
=pending_experiences= is host-only batch selection. =record_experience= and
standalone insertion/mutation tools are not exposed to the judge.
Pin =get_experience=/history/review to the selected identities and revisions;
constrain retrieval to the selected experience's project and bounded results.
Reads may include global context under existing visibility rules; writes may
not. Refuse arbitrary tools, standalone insertion, raw SQL, wrong projects,
out-of-batch review requests, stale sources, malformed arguments, and unsupported
schemas before dispatch. Do not relax these checks for a harness backend.

=[llm].max_calls= provides two independent counters: model invocations and total
model-requested tool executions. Reserve one unit before each attempted call;
failed attempts and retries consume units. Check allowance before execution.
The formal trace conserves the sum of remaining counters and executed calls;
one counter cannot borrow unused units from the other. Trusted batch fetch and
completion reads are separately bounded by batch size, paging, and I/O deadlines.
All provider, MCP, and subprocess waits need finite deadlines and bounded input/
output; budget arithmetic alone does not prove termination of blocked I/O.
Timeout ends the affected attempt and process cleanup includes descendants.

A crash before commit leaves work pending; a crash after commit but before the
status write requires reading the committed state on the next invocation. The
state-directory lock prevents cooperating invocations sharing that directory;
it does not exclude runners using different directories. Database CAS and
atomicity remain mandatory. Write the local report atomically, without treating
that filesystem operation as a distributed transaction with PostgreSQL.

**** Notification transitions

Learning status and notification status are independent fields. Disabled email
is =disabled=; no due alert is =not_needed=. A due enabled alert enters the outbox
with a bounded attempt count. Each actual delivery attempt consumes one attempt;
SMTP acceptance produces =sent=, a failure with attempts remaining produces
=retry_pending= with a due time, and no remaining attempts produces =exhausted=.
Do not sleep for repeated deliveries inside a judge run; future scheduled
invocations retry due items. A successful idle learning run may still retry mail.
Keep a stable local alert identity to avoid generating a new outbox item for
every recurrence of the same unresolved incident. Exact fingerprint, recovery
reset, and backoff encoding are Step 8 implementation details to review there.

=Judge.Notification= proves failed attempts cannot be marked sent, retries spend
their remaining allowance, and every notification transition preserves the
arbitrary learning state. Report exhaustion locally; do not recursively email
about an email-delivery failure. Authentication expiry blocks the affected
backend and leaves work pending; it must not trigger provider/model fallback.
Email is useful only when its own independent credentials still work.

SMTP acceptance is not inbox delivery. A crash after acceptance but before the
outbox write can cause a duplicate email on retry; ordinary SMTP cannot provide
exactly-once delivery. OAuth refresh, server replies, token rotation, clocks,
and private atomic file replacement are adapter obligations, not Agda theorems.
