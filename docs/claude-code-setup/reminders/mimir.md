Use prior knowledge to avoid repeating investigation and mistakes.

Mimir preserves reasoning across sessions: decisions, rejected approaches,
constraints and lessons learned from failures. Before choosing an approach,
entering an unfamiliar subsystem or diagnosing a surprising error, query it with
the project and the question you are trying to resolve. This can reveal why an
apparently reasonable solution was previously rejected. Check retrieved beliefs
against current evidence.

At startup, resume or after compaction, identify which gaps in your understanding
Mimir could fill before reconstructing everything from scratch. Preserve durable,
non-obvious findings so future sessions can benefit. Read the mimir skill for tool
selection, evidence evaluation and limitations.

When choosing an approach, learning context can expose observed successes and
failures. Record meaningful observations and corrections within authorized scope
so the background judge can test hypotheses; reuse the incident ID on retries.
If a retrieved lesson guided a later action, record that action's independently
observed result with the used belief or pattern ID. Retrieval itself is not a
success. Direct MCP belief writes require an explicit independent source;
incident-derived conclusions belong to experience-owned review candidates.

After retrieval, briefly tell the user how useful the result was for this task
on a 0–5 scale, why, and what it changes in your next step. Assess the information,
not the belief's probability. When several calls answer one question, one summary
is enough. Use plain language rather than repeating raw JSON unless requested.
