# Operation catalogue and intended results

Status: inventory for issue [#56](https://github.com/kamysh/mimir/issues/56). This states the required outcomes and records existing implementation/model locations. A location is not evidence that the required behavior or recovery proof is already implemented.

Baseline: `origin/main` at `a402f463441c677db82863fe4805e30fbfbe7c55`, with the separately prepared 2.3.0 metadata update. The [issue series](recovery-and-agent-interaction-issues.md) tracks implementation gaps.

## Common request and recovery rules

- A malformed request receives the exact field problem and a correction path before any business publication. Missing facts are requested, not invented. Corrected input passes through ordinary admission.
- Missing authority, grounding, retention policy, or other business decisions require a user decision. An agent must not invent a policy to make a request succeed.
- A business write needs a stable logical identity and its original saved outcome before its retry can be treated as safe. Those mechanisms are planned in #119–#124; this inventory does not claim the baseline already provides them.
- Read-only means no business-data mutation. Configuration loading, connection establishment, and startup migrations are separate lifecycle operations below.
- Scope and visibility are part of the result. A project-scoped request cannot silently read or change unrelated private project data.
- Omitted result selection requests all matching records. A supplied selection is positive; zero is an input error requiring correction. Existing conflicting defaults and ceilings are removal work, not accepted exceptions.
- External PostgreSQL atomicity/UUID allocation, provider behavior, standard parsing/serialization, and operating-system scheduling remain declared outside contracts. They are not new low-level proof projects.

## Library-only write entry points

`MimirService.delete_evidence` exists in `crates/core/src/lib.rs`; it removes a grounding relationship and applies the required derived-state change. It needs the same idempotence/recovery contract as `add_evidence`. The baseline has **no CLI evidence-removal command**: `EvidenceCmd` contains `Add` and `List`. Certifying this library entry point does not authorize inventing a new public command.

## Recorded gaps and unresolved decisions

- The baseline dispatcher accepts raw scripts. Existing model locations are not concrete `Recoverable` instances; the new total dispatcher and typed Rust registration remain required work.
- Project deletion uses independently committed cleanup phases. Its existing model follows those phases and does not establish the target ownership-closure retry law.
- Direct belief insertion can publish before embedding and grounding finish. Review-created beliefs also need the independently required prepared vector and indexed support. The intended rows above state the user-approved target, not current verified behavior.
- Stable logical write identities and original saved replies are not yet a uniform public contract. A retry must not be declared safe merely because the original database write was atomic.
- Propagation's numerical completion condition and supported cycle behavior must be made explicit before replacing its iteration cutoff. This inventory does not choose a new tolerance or invent a completion claim.
- The current interfaces contain conflicting default selections, maximums, and zero-as-all conventions. They remain removal work; a caller must receive explicit corrected semantics.
- Missing embedding, indexed grounding, retention policy, or other user-owned decisions cannot be resolved by an agent guessing. Required decisions remain explicit prerequisites.
- CLI hook exposure and library-only operations must be matched to their actual routes. An unused formal constructor is not evidence that a public tool or command exists.
