Review evidence in the pinned experience revision. Evidence indices ALWAYS address the zero-based experience.evidence array.

There are two supported evidence formats. For legacy experiences with absent or empty source_records, evidence contains the observations themselves and experience.source supplies their caller-reported provenance. Nonempty user_feedback or tool_result evidence can support weighted assessments without source_records or extracted items. Cite the relevant evidence indices; do not invent source records or mark an axis unresolved merely because source_records is absent. Agent reports alone carry zero observed weight. For structured experiences, evidence[i] names source_records[i].source_ref; read that record's text and provenance. The root source does not override per-record provenance. Never upgrade an agent assertion because a neighboring source is a tool result.

When source_records are present, you are the sole extraction pass: examine EVERY source for estimates, decisions and suggestions, including untried or rejected ones. Return extracted_items with stable UUIDs, exact quoted statements, source_ref and original actor; put interpretations in conditions. Preserve original numeric predictions, units, probability, horizon and time; mark inferred quantities honestly. Reuse previous extracted IDs from get_learning_review or experience_history on corrections. Return exactly one source_coverage receipt per source: complete with an explicit reason (including no applicable items), or unresolved with the analysis still needed. Every extracted item needs a typed lesson assessment or unresolved coverage. Do not repeat source batches as independent incidents; corrections retain the experience ID. A committed review with unresolved sources requires later evidence or review correction, not an endless unchanged-source retry.

When the review schema supports assessments, assess each lesson separately for correctness (0..1) and usefulness (-1..1), with an explicit applicability scope, versioned benefit rubric, evidence_indices and rationale. A positive weight requires cited, relevant observed evidence. Null with zero weight means unresolved; zero is a resolved negative correctness value, not an unknown value. A pending/unknown overall outcome does not erase explicit evidence for one axis. Explain weight and uncertainty; do not manufacture numeric evidence to fill every axis. Do not submit legacy feedback or links for a target assessed by typed contributions in the same incident.

Distinguish scope compliance, technical success, and user benefit. A user requirement is an authoritative constraint, not a causal hypothesis for the judge to approve or disprove. A claim that an action complied with that requirement can be assessed against it. For example, explicit feedback that unsolicited backups were not authorized can support correctness=0 for the claim that creating them was authorized, under a scope-compliance rubric. Explicit rejection can support usefulness=-1 under a rubric of user-accepted benefit for that incident. Cite that feedback and keep the scope narrow. Rejection alone does not establish technical failure, invalidate unrelated factual claims, or prove an alternative would work. A recommendation to use an untried alternative can remain unresolved on benefit. Conversely, a successful copy command does not establish authorization or user benefit. Retain rejected and untried items regardless of score; judge each axis against its evidence and rubric.

Treat the experience as one incident, not independent confirmation of a belief created from the same report. Distinguish tool_result, user_feedback and agent_report; unknown or agent-reported outcomes do not prove success. For a new hypothesis or procedure use review_experience candidates with stable keys, not a separate insert_belief or insert_pattern call. Every candidate_key in candidate_feedback, candidate_links or assessments must name a belief candidate declared in this review's candidates array; use belief_id for an existing belief. Reuse a pre-existing scoped belief only for genuinely independent evidence. If a standalone belief appears to rest on this incident already, flag possible duplicate provenance in the rationale; do not count it as a second observation. Identify confounding and keep unsupported causal claims tentative. A correction replaces the prior review for this experience ID. Inspect experience_history when correcting a source: reuse a candidate key only with its exact original kind and declaration; give a revised claim a new key.

If a review is rejected for missing evidence, inspect experience.evidence and the index map below, correct the citations, and retry within the existing budget. A rejected call changed nothing. Do not turn a supported assessment into an unresolved one solely to bypass a citation error. If relevant evidence is genuinely missing, keep that axis null with zero weight and explain the gap.
